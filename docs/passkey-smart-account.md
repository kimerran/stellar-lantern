# Passkey smart accounts (#53)

A seed-phrase-free Stellar account whose **signing key is a device passkey**
(WebAuthn, NIST P-256 / secp256r1). There is no mnemonic and no Ed25519 secret:
the account is a **Soroban custom-account contract** that authorizes operations
by verifying WebAuthn assertions on-chain with the protocol-21
`secp256r1_verify` host function. This is #23's Milestone 2b, unblocked by the
#21 Soroban invoke pipeline.

Flag-gated behind `VITE_FEATURE_PASSKEY` (default **OFF**), testnet-only.

## How authorization works

Soroban gives `__check_auth` a 32-byte **signature payload hash** (over network
id, nonce, expiration ledger, and the invocation tree). The wallet uses that
hash as the **WebAuthn challenge**:

```
payload = sha256(HashIdPreimage::SorobanAuthorization{network, nonce, expiration, invocation})
assertion = navigator.credentials.get({ challenge: payload, ... })
signature ScVal = { authenticator_data, client_data_json, signature(r‖s, low-S) }
```

On-chain, the contract:
1. verifies the P-256 signature over `authenticator_data ‖ SHA-256(client_data_json)`
   against the bound public key (`secp256r1_verify` traps on failure), and
2. requires `client_data_json`'s `"challenge"` to equal base64url(payload) —
   exactly 43 chars, closing quote checked — so an assertion for one payload
   can never authorize another.

The send pipeline (`transfer.ts`) is deliberately two-phase so the **scan →
approve gate sits between them** — the same discipline as the classic Send
screen, no bypass lane:

```
prepare  = build SAC transfer → simulate → assemble          → scan() → user approves
finalize = passkey-sign auth entries → RE-simulate (enforce) → re-assemble
caller   = sign envelope with fee payer → SUBMIT_ONLY
```

The re-simulation runs in enforcement mode (signatures attached), so a bad
assertion fails *before* broadcast, and the footprint/fee are refreshed to
include the `__check_auth` cost.

## Fees: the ephemeral fee payer

A Soroban transaction's source must be a classic (G…) account; a contract can't
pay its own inclusion fee. On **testnet** the wallet mints an ephemeral
`Keypair.random()`, friendbot-funds it, and uses it as deployer (onboarding)
and fee source (sends). It is never persisted; it controls nothing — the smart
account answers only to the passkey. **Mainnet** needs a real fee-sponsorship
channel (e.g. Launchtube or an app-operated sponsor); that is the explicit
follow-up before this feature can leave testnet.

## Guardian recovery interop (#23 M1)

#23 M1 shipped guardian social recovery for **classic accounts** using native
Stellar multisig: guardians are additional Ed25519 signers with thresholds, and
recovery co-signs a `setOptions` key-rotation via `SIGN_ONLY`.

A passkey smart account has **no signer list on the classic account** — the
contract *is* the account, and today it binds exactly one passkey with no
rotation entrypoint (deliberately minimal MVP). Recovery therefore maps to the
contract layer, not `setOptions`:

- **Guardians become contract-level co-signers.** The natural extension is a
  `signers` map in contract storage (passkey + N guardian keys — Ed25519
  addresses or other passkeys) plus an `add_signer` / `rotate_passkey`
  entrypoint whose auth policy requires a guardian quorum (`require_auth` on M
  of N guardian addresses). Soroban makes the quorum check explicit contract
  logic, which is *stronger* than classic multisig (arbitrary policies, e.g.
  time-locked recovery).
- **What recovery recovers.** Losing the device loses the passkey, but the
  account (and its funds) live at the contract address. With guardian signers
  in place, a quorum authorizes binding a NEW passkey's public key; the old
  credential simply stops mattering. No seed phrase is ever part of the story.
- **What exists today.** The MVP contract is single-signer with no rotation:
  lose the passkey and the account is unrecoverable (like losing a seed phrase
  with no guardians). The UI says "no seed phrase exists" and treats the
  account as testnet-experimental. Adding the guardian-signers entrypoint +
  recovery flow is the tracked follow-up for taking 2b beyond MVP; #23 M1's
  guardian UX (invite, quorum, co-sign) carries over — only the co-signed
  payload changes from a classic `setOptions` to a contract invocation.

## Known limits / caveats

- **Testnet only** (friendbot is the fee sponsor). Mainnet blocked on fee
  sponsorship + a contract audit.
- **No signer rotation yet** — see the guardian section above.
- **rpId / platform**: WebAuthn inside a Chrome extension popup uses the
  extension origin; on-device behavior should be validated per Chrome version
  (the core is device-independent and covered by the fake-authenticator e2e).
  The passkey path is hidden on the native (Capacitor) build.
- **Contract instance TTL**: testnet entries can expire/archive after long
  inactivity; a production build should `extend_ttl` periodically.
- **Balance display** covers native XLM only (SAC `Balance` entry); other
  assets and history views are follow-ups.
