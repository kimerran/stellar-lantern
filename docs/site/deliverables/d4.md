## What a user can do when this is done

Anyone can open [golantern.xyz/demo](https://golantern.xyz/demo/) on a phone or a laptop and:

- **Paste** any Stellar testnet transaction, or **compose** a payment from two addresses and an amount, and see what it would move, to whom, the risk verdict, one plain-language sentence, and whether each counterparty is in the scam registry. Nothing asks for a key, and nothing is signed or submitted.
- **Run six built-in examples**, including a payment to a reported scammer that is caught every time. Each runs live first. When the network can't be reached it replays a recorded copy and says *Using cached simulation*.
- **Browse the registry**: every reported address, its reason, status, report count and reporter, read straight from the ledger with no account.
- **Report an address**, signed by their own Stellar wallet (Albedo works in the browser with nothing to install). Lantern scans the report transaction first, like any other, and the address reads as reported straight afterwards.

A registry answer that can't be read shows as *Not checked — unverified*, never as clean.

## Scope notes

- **Testnet only.** The playground has no network switch. Mainnet has no registry, so a mainnet scan could only say "not checked" for every counterparty.
- **Nothing is signed except a report**, and a report is signed by the visitor's own wallet. A web page cannot reach the Lantern extension, so the playground uses the visitor's Stellar wallet rather than a bridge into ours, which would be exactly the surface wallet phishing attacks.
- **Our own contract gets no shortcut.** The report transaction is scanned like any other before the wallet sees it, and it reads *Caution* (a contract Lantern treats as unverified). That is the rule working, not a bug.
- **Example clicks are never counted as scans.** One click on a built-in example is reported separately and never added to §6.3's "transactions scanned end-to-end". Otherwise sixty clicks would clear the target.
- **Privacy.** No cookie and nothing stored in the browser; the analytics event carries no address, amount or transaction. The plain-language summary does send the scan's effects to our server and on to the AI provider, unstored, and the [privacy policy](https://golantern.xyz/privacy-policy.html) says so.

## Implementation choices

- **One scanner, two surfaces.** The page imports the same package the wallet does, and the build check fails if the scan pipeline isn't in the bundle, so "the same scanner" is checked on the output, not asserted.
- **A committed, drift-checked build.** The homepage is a static site, so the playground's build output is committed and the test lane rebuilds it and fails on any difference, the same arrangement as this evidence site.
- **Recorded fixtures as the offline fallback.** The examples replay the scanner test suite's own recorded testnet responses, so the demo survives a slow or reset testnet and the recording is reproducible on any day.
- **The registry panel reads ledger entries.** `count()` and `list()` need a simulated transaction and a source account; a visitor has none. The panel reads the contract's instance, index and entries directly: three requests for the whole registry, not one per entry.
- **Wallet code loads on demand.** The four wallet connectors are fetched only when a visitor opens the wallet list, so the page's first load is unchanged.
