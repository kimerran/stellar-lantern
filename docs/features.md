- 2026-09-08 — On-chain blacklist registry: **public read API** (`contracts/blacklist-registry/src/lib.rs`). Slice 4 of Deliverable 1, the surface the SOW promises any wallet or dApp can query: `is_flagged(subject) -> bool`, `get(subject) -> Option<Entry>`, `count() -> u32`, `list(start, limit) -> Vec<Entry>` and `config() -> Config`. None of the five takes `require_auth` — screening a counterparty must not require an identity, let alone a signature, or the registry stops being a public good. `is_flagged` is true **only** for `Status::Active`: a disputed entry's evidence is contested and a revoked one has been cleared, so neither raises a warning, which is the whole reason the status machine exists. An address nobody ever reported is a plain `false`, never a panic — this runs on every counterparty of every transaction. `list` pages in insertion order with `limit` capped at `MAX_PAGE` (50, `Error::InvalidLimit` outside `1..=50`); a `start` past the end returns an empty `Vec` rather than erroring, so a caller can page to exhaustion without special-casing the last page, and an index slot with no entry behind it is skipped rather than panicked on, so one such slot can't brick paging. `count` tracks distinct subjects, not reports. `list` reads entries directly and refreshes no entry TTL — a bulk indexer sweep should not rewrite the whole registry's TTL, and it keeps a full page to one write rather than one per row. The per-subject reads do refresh, through a shared `load` helper: the entries wallets keep asking about are exactly the ones that must not expire, and the read path is the best signal available about which still matter — `extend_ttl` stays a no-op until the remaining TTL falls under the threshold, so a read on a fresh entry costs nothing. These are the *simulation-based* views; the cheaper per-signature hot read (`getLedgerEntries` on `DataKey::Entry`, no source account and no fee) is #44. 15 new tests cover every status for `is_flagged`, full-entry fidelity against storage, distinct-subject counting, insertion order, pagination including the short last page and past-the-end, both `InvalidLimit` boundaries, a missing entry mid-page, reads succeeding with no auth mocked at all, the TTL refresh on both sides of the threshold, and — asserted from inside the bump threshold, where a refreshing read would visibly move it — that paging refreshes no entry TTL while a per-subject read still does. - 2026-09-08 — On-chain blacklist registry: **admin status transitions + config management** (`contracts/blacklist-registry/src/lib.rs`). Slice 3 of Deliverable 1: `set_status(subject, status)` moves an entry between `Active` / `Disputed` / `Revoked`, and `set_admin` / `set_treasury` / `set_fee` / `set_fee_token` manage the config. Disputes are how a wrongly-flagged address stops producing a warning **without deleting the record** — the entry is never removed, so who reported what and how it was resolved stays readable on-chain. All five load `Config` and `require_auth()` the *current* admin before touching anything else (a shared `require_admin` helper), so nothing about the registry is observable to an unauthorized caller. `set_admin` additionally requires the **incoming** admin's authorization: there is no upgrade entry point and no recovery path, so a hand-off to a mistyped or uncontrolled address would be terminal — both signatures ride in the same transaction, so a compromised key is still rotated in one call. `set_status` on a subject with no entry is `Error::NotFound` rather than an implicit create, so the admin can't flag an address without a fee-paying report behind it; it bumps the entry **and** its insertion-index key together, the same invariant `report()` holds. Any transition is allowed, including a same-status no-op: a transition matrix could strand an entry in a state the admin can't leave. `Revoked` is deliberately **not** durable — the next `report()` re-flags the subject, so the admin can clear current evidence but cannot silence an address forever, and `set_fee` is the lever if re-flagging should cost more. `set_fee` rejects a negative fee (`Error::InvalidFee`, same rule as the constructor) and accepts `0`; a repriced fee, a re-pointed treasury and a switched fee asset all apply to the *next* report, while fees already collected stay put — the contract never custodies them. Every change emits an event carrying **both sides** — `(status, subject) -> (old, new)` and one topic per config field (`(config, admin|treasury|fee|fee_token)`) — so an indexer never has to carry state across events to know what was replaced. 16 new tests cover the admin gate on all five entry points, the two-signature hand-off, the unknown-subject path, a full state cycle with advancing `updated_at`, entry preservation, fee/treasury/fee-token re-routing, and the event shapes. The contracts CI lane also gained a **vendored-wasm staleness gate**: it now `cmp`s the freshly built artifact against the `.wasm` committed next to each crate, so a PR that changes a contract but forgets its `scripts/build-*.sh` fails instead of shipping a stale blob that #36 would publish a hash from. - 2026-09-07 — On-chain blacklist registry: **fee-gated `report()` write + treasury routing** (`contracts/blacklist-registry/src/lib.rs`). Slice 2 of Deliverable 1, the heart of it: `report(reporter, subject, reason, evidence) -> u32` records an address as malicious and charges `Config::fee` of `Config::fee_token` from the reporter to the project treasury. The fee *is* the anti-abuse mechanism — spamming the registry costs money — and it funds the scanner's AI inference. Order of operations is deliberate: `reporter.require_auth()` runs **first**, before any storage read or transfer, so nothing about the call is observable to an unauthorized caller; self-reports are rejected with `Error::SelfReport`; then the fee moves, then the entry is written. The fee is charged on **every** accepted report, including repeat reports of an already-flagged subject (that is the anti-spam property); a `fee == 0` config skips the transfer entirely, which is how the registry runs on testnet before a treasury is funded. Upsert semantics encode the audit trail: a **new** subject is written `Active` with `reports = 1` and appended to the insertion-ordered index; an existing **Active or Disputed** entry only increments `reports` and `updated_at`, deliberately keeping the *first* reporter, reason, evidence and `reported_at` so a later reporter can't rewrite who said what (and a disputed entry stays disputed — only the admin resolves a dispute, #33); an existing **Revoked** entry is reactivated under the new reporter's attribution but keeps the original `reported_at`. Repeat reports never touch `Count` or add an index slot, so the subject list stays duplicate-free. Every write bumps the entry's and the instance's TTL, then publishes `(("report", subject), (reporter, reason, status, reports))` — replaying that event gives an indexer the flagged set and, per subject, the current attribution, reason, status and report count — it is deliberately **not** the whole entry (`evidence`, `reported_at` and `updated_at` are not in the payload, so an indexer that needs those reads contract storage once the views land in #34). The topic/data shape is fixed by the spec, so the SDK-27 `#[contractevent]` migration (which would change that wire format) is left as a deliberate follow-up. **Review follow-up (TTL):** `Index(i) -> subject` is a *separate* persistent ledger entry from `Entry(subject)`, and a freshly written one starts at the network **minimum** persistent TTL — the first snapshots showed index records at 4,095 ledgers while `Count` and the entry sat at 1,036,800. Left alone, the index expires under a live subject: `Count` and `Entry(subject)` still say the address is flagged while `list()` (#34) can no longer enumerate it, and every repeat report widened the gap because it refreshed only the entry. Fixed by making the ordinal recoverable from the entry itself — `Entry` now carries `index: u32` — so `bump_entry` extends `Entry(subject)` **and** `Index(entry.index)` together, on the first report and on every repeat. Two regression tests pin it (initial and repeat report, asserting index TTL == entry TTL); both fail with `left: 4095, right: 1036800` when the index bump is removed, and the regenerated snapshots now show a single TTL, 1,036,800, across all four records. **Review follow-up (event payload):** the `report` event now publishes the **persisted** attribution — `entry.reporter` / `entry.reason`, not the call's arguments. On a repeat report of an already-Active/Disputed subject the entry deliberately keeps the FIRST reporter and reason, so emitting the caller's made an indexer that folds these events into state diverge from storage; a regression test reports a subject twice under different reporters/reasons and asserts the second event matches `Entry` (it fails `left: (…, Mixer, Active, 2)` vs `right: (…, Drainer, Active, 2)` on the old payload). The revoked reactivation path is unaffected: it rewrites the entry's attribution, so the event carries the new reporter either way. Verified: 19 unit tests green against a mock SAC registered in-test — fee actually moves reporter → treasury, an unfunded reporter's call reverts whole (no entry, `Count` still 0), a repeat report charges the fee again without growing the index, a missing reporter auth fails, revoked reactivates, disputed stays disputed, zero fee skips the transfer, and the emitted event's topics and data are decoded and asserted field-by-field. `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` clean; WASM 7,754 bytes, sha256 `40396b7a…`, exporting `__constructor` + `report`. No `src/` (TypeScript) change. Part of kimerran/internal-lantern#32.
